# Evaluation Rubric

| Evaluation Criteria | Points | Level 5: Exemplary (100%) | Level 4: Proficient (80%) | Level 3: Developing (60%) | Level 2: Beginning (40%) | Level 1: Inadequate (20%) |
| :--- | :---: | :--- | :--- | :--- | :--- | :--- |
| **OOP Architecture & Abstraction** | **25** | Flawless implementation of encapsulation, inheritance, polymorphism, and abstract components. Subtypes clearly extend behavior cleanly; zero code duplication. | Correct inheritance and encapsulation. Subtypes override base methods properly with minor architectural redundancies or light coupling. | Inheritance present, but misuse of abstract/virtual members occurs. Partial encapsulation with unnecessary public fields. | Weak class structure. Relies heavily on procedural logic wrapped in classes; missing polymorphism or inheritance. | Non-functional or absent object-oriented structure. Purely procedural script; no custom classes or objects utilized. |
| **Domain CRUD & Reporting Logic** | **25** | All CRUD operations, search, aggregate calculations, and state alerts function flawlessly across all concrete domain entities. | Core CRUD features execute correctly. Minor bugs in threshold reporting or non-critical edge cases. | CRUD functionality works for some subtypes but fails or behaves inconsistently on others. Reporting logic is incomplete. | Only basic creation or listing works. Updating, deletion, or reporting are missing or broken. | Major functional deficiencies. System fails to perform basic creation or retrieval of domain entities. |
| **Persistence & File I/O** | **10** | Complete automated file I/O using `IPersistable`. System flawlessly loads, deserializes, updates, and saves entire entity state upon program startup and shutdown. | Reliable persistence for core data. Minor edge cases in parsing specific data fields, or user must save manually before exit. | File I/O works for basic data, but fails to reconstruct complete object relationships (e.g., losing associated `TransactionRecord` logs). | Persistence is partially implemented but frequently corrupts data or fails to reload saved states across application restarts. | File I/O is completely missing, non-functional, or causes fatal errors upon file read/write operations. |
| **Exception Handling & Validation** | **10** | Custom exception hierarchy implemented. Input validation completely prevents terminal crashes from invalid data types or out-of-bound domain states. | Custom or standard exceptions handled well. Common invalid inputs are caught and re-prompted gracefully; minor edge cases remain. | Basic exception handling present (try-catch), but system relies mostly on standard exceptions without custom domain errors. | Minimal validation. Unhandled exceptions occur frequently on bad user input, leading to premature application termination. | No input validation or exception handling present. Any improper user entry crashes the program immediately. |
| **UML & Documentation** | **30** | Production-quality UML class diagram following standard notation (attributes, methods, visibility, relationships). Complete domain map and clear source code comments. | Accurate UML diagram with minor notation errors (e.g., misidentified aggregation vs. composition). Source code is reasonably documented. | UML diagram included but incomplete (missing relationships or methods). Sparse comments throughout source code. | Poorly structured UML diagram resembling a basic flowchart rather than OOP structure. Minimal or missing documentation. | UML diagram and domain documentation are completely missing. Source code contains no comments or structure. |
| **Total Points** | **100** | | | | | |
